## 二、核心问题总结

### 问题1：LLM返回格式不稳定（致命）

**现象**：
- 前2张截图：LLM返回分析文本（reasoning_content），JSON解析失败
- 第3张截图：LLM正确返回JSON数组

**根因**：
- DeepSeek模型有时会返回`<think>...</think>`或自然语言分析过程
- `_parse_llm_json` 期望整个文本是JSON，无法从混合文本中提取
- `ai_gateway` 的 `content为空，回退使用reasoning_content` 机制把分析文本当作了正式输出

**影响**：
- 3张截图中2张的LLM提取完全失效
- 正则兜底在第二张截图也崩溃了
- 最终3张截图中只有1张完整提取，1张部分提取，1张完全失败

### 问题2：正则兜底不够健壮

**现象**：
- 第二张截图正则提取崩溃：`ValueError: could not convert string to float: ''`

**根因**：
- `_find_amount_in_line` 中 `m.group(1)` 可能匹配到空字符串（regex alternation的边界情况）
- `_parse_num` 没有处理空字符串

**状态**：源码已修复，但 dist 目录可能仍使用旧版本

### 问题3：LLM提取链路没有利用LLM的识别能力

**现象**：
- 从日志可见，LLM（即使返回文本形式）实际上正确识别了所有持仓
- 但程序只接受严格JSON格式，导致这些识别结果被丢弃

**本质**：
- LLM是"看懂"了截图内容的（前两张截图的分析文本中准确描述了持仓）
- 但程序的JSON解析器"看不懂"这种自然语言输出
- 这是**接口不匹配**问题，不是LLM能力问题

## 三、当前数据流链路

```
截图 → OCR文本 → LLM提取 → JSON解析 → 写入DB → 前端展示
                ↓ 失败时
              正则兜底 → 写入DB
```

**断裂点1**：LLM返回自然语言 → JSON解析器失败 → 数据丢失
**断裂点2**：正则兜底崩溃 → 整个文件处理失败 → 数据丢失

## 六、修复方向

1. **增强JSON解析**：从混合文本中提取JSON数组（使用regex匹配`[...]`模式）
2. **LLM输出强制**：在system prompt中更严格要求只返回JSON，或使用response_format
3. **备用提取**：当LLM返回文本而非JSON时，尝试用regex从文本中提取关键信息
4. **确保dist同步**：正则空字符串保护必须生效
5. **国债收益率**：改用新浪财经/东方财富备用API，或LLM查询
